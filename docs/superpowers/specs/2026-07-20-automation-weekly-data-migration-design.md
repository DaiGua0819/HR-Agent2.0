# 近七日招聘数据一次性迁移设计

## 背景

招聘数据仪表盘已经部署到预览服务，但新建的 `automation_contact_events` 和
`automation_runtime_status` 表没有历史数据，因此每日指标显示为 0。现有本地数据库仍保存
候选人会话、消息、决策、处理快照、简历和 Agent Manager 运行记录，数据并未丢失。

本次不建设新的长期本地监控同步通道。只把当前近七个北京时间自然日的候选人处理数据整理后
一次性迁移到服务器。后续招聘账号迁移到服务器运行后，由服务器 Worker 直接产生新数据。

## 目标

- 一次性迁移近七个北京时间自然日的数据，包含当天在内。
- 同一候选人在同一天只统计一次，并在明细中展示最新处理结果。
- 候选人当天发生过的业务动作采用累计状态，每个动作最多计一次。
- 迁移包可以重复导入，不产生重复记录。
- 仪表盘默认显示今日数据且不再错误显示全 0。
- 暂时隐藏账号平台状态，不要求服务器提前登录招聘账号。
- 日期控件显示两位年份，例如 `26/07/20`，内部继续使用 `2026-07-20`。

## 非目标

- 不新增本地到服务器的长期监控同步进程。
- 不停止或重构现有简历、聊天记录 Auto Sync。
- 不迁移浏览器 Profile、Cookie、Token 或其他登录凭据。
- 不处理服务器招聘账号登录和平台心跳。
- 不重算七天以前的历史招聘指标。

## 日期范围

迁移范围使用 `Asia/Shanghai` 自然日。以 `2026-07-20` 执行为例，范围是：

```text
2026-07-14 00:00:00 +08:00
至
2026-07-20 23:59:59.999999 +08:00
```

每个候选人可以在不同日期各出现一次，但同一天只能产生一个每日投影。

## 候选人身份

候选人每日投影优先使用以下稳定身份：

1. `conversation_sessions.id`。
2. `platform + owner + platform_conversation_id`。
3. `platform + owner + conversation_id`。
4. 最后才使用 `platform + owner + candidate_name + job_type`。

无法得到平台、负责人或任何稳定会话身份的记录不直接合并，列入 dry-run 的未解析清单，避免
把同名候选人错误合并。

每日投影 ID 使用以下逻辑生成：

```text
automation-daily:{yyyy-mm-dd}:{sha256(stable_candidate_identity)}
```

重复执行导出或导入时会覆盖同一条每日投影，而不是新增重复数据。

## 数据来源

投影器按可靠性从高到低组合现有数据：

1. Agent Manager `data/agent_manager/runs/*.jsonl`：联系人处理结果、平台、负责人、动作和异常。
2. `message_processing_snapshots`：规范化处理身份、阶段、动作和最终处理状态。
3. `conversation_sessions`：候选人姓名、岗位、平台、负责人和最近更新时间。
4. `conversation_messages`：候选人提问、公司回复和最后消息时间。
5. `resumes` 与 `resume_artifacts`：51job、智联简历获取及可下载简历关联。
6. `decision_logs`：补充动作、规则命中和回复结果；不单独用于推断平台或负责人。

dry-run 必须输出三类覆盖率：

- 精确关联：使用 session 或平台会话 ID 关联。
- 降级关联：使用平台、负责人、姓名和岗位组合关联。
- 未解析：缺少稳定身份，未进入迁移包。

## 每日投影语义

每日投影继续写入现有 `automation_contact_events`，不再新增一张重复用途的表。

最新一次处理结果提供：

- `occurred_at`
- `action`
- `stage`
- `candidate_name`
- `job_type`
- `owner`
- `platform`
- 明细页展示内容

当日所有已确认处理结果累计以下布尔字段：

- `processed`
- `sent_company_info`
- `requested_resume`
- `candidate_question`
- `knowledge_answered`
- `resume_acquired`
- `anomaly`

例如同一候选人先发起求简历，之后又回复问题，最终只显示后一条最新处理记录，但
`requested_resume` 和 `candidate_question` 都保持为真。

业务简历获取遵循现有平台合同：

- BOSS：求简历动作经验证成功即计入业务简历获取，不要求本地 PDF。
- 51job、智联：附件或在线简历实际下载并形成有效文件哈希后计入。

## 一次性迁移流程

1. 本地脚本默认 dry-run，读取近七日数据并生成每日投影统计。
2. dry-run 输出每天、平台、负责人、岗位、动作和未解析数量。
3. 使用 `--export` 生成 UTF-8 JSON 数据包，不写本地业务表。
4. 数据包上传服务器暂存目录并计算 SHA-256。
5. 服务器导入脚本默认 dry-run，验证日期范围、字段、候选人身份和重复 ID。
6. 使用 `--apply` 后通过 `ON CONFLICT(id) DO UPDATE` 幂等写入。
7. 导入前使用 SQLite backup API 备份服务器数据库。
8. 导入后比较本地导出统计与服务器聚合统计。

迁移完成后不保留新的定时任务，也不启动新的本地同步进程。

## 服务器聚合

统计服务先按稳定候选人身份和自然日归并，再计算 KPI。为兼容未来服务器 Worker 直接写入的
普通处理事件，聚合逻辑需要：

- 按 `contact_key` 识别同一候选人。
- 最新事件提供明细展示字段。
- 同日所有事件的动作布尔字段采用 OR 合并。
- 每个指标中每位候选人最多计一次。
- 跨日期不去重。

明细分页继续固定每页 10 人，简历链接仍通过已有简历关联逻辑生成。

## 前端调整

- 暂时隐藏“账号平台状态”区域及其轮询。
- 岗位处理分布扩展到原账号状态区域，减少空白。
- 日期值内部保持 ISO `YYYY-MM-DD`。
- 页面显示使用 `YY/MM/DD`，例如 `26/07/20`。
- 使用自定义日期按钮和弹出日历，避免原生 `input[type=date]` 强制显示四位年份。
- 选择日期、前后切换日期和 URL 参数仍传递完整四位年份。
- 日期无数据时显示明确空状态，不伪造统计。

## 错误处理

- 未解析候选人只报告，不猜测身份。
- 无效日期或超出近七日范围的记录不进入迁移包。
- 数据包哈希不一致时拒绝导入。
- 导入中任一记录校验失败时整批回滚。
- 重复导入返回更新数量和未变化数量。
- 本地导出与服务器统计不一致时不完成验收。

## 测试

- 同一候选人同日处理三次，处理联系人只计 1 人。
- 最新动作和时间来自第三次处理。
- 第一次发生的求简历动作在最新投影中仍为真。
- 同一候选人跨两天处理时每天各计 1 人。
- BOSS 已验证求简历计入业务简历获取且不要求本地文件。
- 51job、智联只有有效下载文件时计入业务简历获取。
- 同名但不同平台会话的候选人不被错误合并。
- 导入相同数据包两次，服务器记录总数不增加。
- 近七日每天的导出数量与服务器聚合数量一致。
- 日期显示为 `YY/MM/DD`，API 参数仍为 `YYYY-MM-DD`。
- 账号状态区域不显示，也不再发起状态轮询。
- 每日明细保持每页 10 人，简历下载链接可用。

## 验收标准

- 近七日有处理记录的日期不再显示为全 0。
- 今日处理联系人等于本地每日投影中的唯一候选人数。
- 同一候选人当天明细只出现一次。
- 各动作人数等于每日投影累计标记的候选人数。
- 岗位、平台和负责人筛选结果与迁移包统计一致。
- 日期栏显示两位年份。
- 服务器数据库备份可用，`8080` 服务不受影响。
- 未来账号迁移到服务器后，服务器 Worker 可以继续沿用同一聚合口径写入数据。
