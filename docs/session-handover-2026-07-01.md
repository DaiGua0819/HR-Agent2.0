## 6. 三平台消息处理核心规则

共享业务逻辑在重构版中应统一走：

- `ConversationRunner`
- `app/agent/rules.py`
- `app/agent/screening.py`
- `app/agent/policy.py`
- 平台只做页面适配、读取、点击、发送、下载。

岗位规则来源：

- `config/chat_rules/boss_chat_rules.json`
- 不要只看 `positionReplies`。
- 要同时匹配 `companyKnowledgeBase.sections`。
- section 通过 `title / aliases / matchPositions` 匹配岗位。
- `screening.questions` 中 `text + variants` 是同一个问题的不同问法：
  - 发送时随机选一种。
  - 判断是否问过时，主问法和任意 variant 都算同一个问题。
  - 不能把 variants 当成额外问题重复问。

筛选模式：

- `ask_required_questions`
  - 所有必问问题都明确接受，才求简历。
  - 任意一个必问问题明确拒绝，就跳过。
  - 含糊或未回复，就等待或继续问下一个。
- `ask_any_required_question`
  - 任意一个必问问题明确符合，就可以求简历。
  - 只有所有问题都明确不符合，才跳过。
  - 含糊或未回复，就等待或继续问下一个。

候选人问问题时：

- 先走岗位知识库答疑。
- 知识库没有答案不要编造，记录为未知问题/待补充。
- 如果对方满足筛选并追问已知问题，先答疑，再继续求简历。

## 11. 候选人状态与简历桥接方案记忆

用户已确认的方向：

- 处理消息和简历入库解析必须拆开。
- 处理消息时只创建/更新平台会话状态和下载 artifact。
- 简历姓名 `parsed_name` 先允许为空。
- 后续简历进入简历库解析时，再补写 `parsed_name`。
- 主关联依据不是简历姓名，而是下载发生时的 `session_id`。

设计目标：

- `conversation_sessions`
  - 用 `platform + owner + platform_conversation_id + position` 定位候选会话。
  - 没有平台 ID 时，用 `candidate_name + position + recent_messages_fingerprint` 兜底。
- `conversation_messages`
  - 按 `session_id + message_hash` 去重保存聊天历史。
- `candidate_status`
  - 保存已问问题、下一问题、是否已求简历、是否已收到/下载简历、当前阶段、最近动作。
- `resume_artifacts`
  - 下载成功立刻写入 artifact。
  - 初始 `parsed_name` 为空，解析后回填。

注意：

- `resume_requested=True` 只表示已经发起求简历。
- 不能把 `resume_requested=True` 当成“简历已完成”。
- 只有真实收到/下载简历并写 artifact 后，才算 `resume_downloaded=True`。
- dry-run 下不能把求简历/下载写成真实完成态。
